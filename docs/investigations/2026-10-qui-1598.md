# Shared stream queues (`QUI-1598`)

All 18 first-pass matrix cells pass on this host at both read counts.
A repeat with the final test fails at 32 sessions and 128 reads with 32 connections.
It returns 0/32 sessions at the 900-second deadline.
Pre-arming kernel exit makes the same cell finish in 1.521778126 seconds.
The inverse patch removes the temporary change.
The observed failure supports H1, but its hardware queue cycle remains unproven.

## Reproduction

The ticket reports 48 concurrent MSA sessions on an RTX A4000 with `CUDA_DEVICE_MAX_CONNECTIONS=32`.
Each session receives one job with 2,108 nodes, 8,192 sweeps, and 64 reads.
The ticket reports zero results after seven hours.
Its 128-read control completes on another GPU in about two minutes.

The ignored test `tests/concurrent_sessions_gpu.rs` uses the degree-4 ring from the task brief.
Each session owns two CUDA streams and receives one job through a closed input channel.
The test requires every `run_stream` call to return a successful result before a shared 900-second deadline.
It prints the count and elapsed time before it fails on a hang.

## Hypotheses

H1: stream queues can put a transfer behind another session's persistent kernel.
The resulting cycle prevents the exit writes from reaching either kernel.
H1 predicts a hang risk when the stream count exceeds the connection count, at both read counts.

H2: the one-word MSA path itself stops responding.
A hang with one session and 64 reads would make H2 the lead hypothesis.

## Pre-arm experiment

The experiment calls `set_exit_now(nonce_id)` after each cold-slot upload in `run_session`.
That helper writes `EXIT_AFTER_MODEL`, which `bench_one` also uses.
The existing transfer synchronization commits those writes before kernel launch.
The graph, streams, read count, sweep count, and 900-second deadline stay unchanged.

The experiment repeats the failed cell with `CUDA_DEVICE_MAX_CONNECTIONS=32` and `QUIP_SESSIONS=32`.
It uses `QUIP_READS=128`.
Its GPU check still shows processes 519901 and 520268 on devices 0 and 1.

The run reports 32/32 sessions in 1.521778126 seconds, with a full test time of 4.92 seconds and exit code 0.
`prearm-32-128.log` keeps the command and each session's time.

The run keeps the experiment uncommitted and removes it with the inverse patch.
`git diff -- src/streaming.rs` is empty after the revert.

## Cause and limits

The reproduced failure strands all session workers inside the CUDA driver after persistent-kernel launches.
Control copies and session setup both stop. No session worker can reach host scoring or finish teardown.
Pre-arming makes each kernel finish its model without a later host exit write, and the measured cell then passes.
This result supports H1's dependence on host traffic reaching running kernels.

The traces also show driver read/write locks and a worker active in `cuStreamCreate`.
They do not establish which hardware queues hold which streams.
The pre-arm comparison includes one failed baseline and one passed experimental run under shared device use.
The cells with 48 sessions also finish in both matrices.
The result supports a scheduling-dependent failure. It does not confirm a deterministic connection-count threshold.

The original ticket's 64-read hang and passing 128-read control remain only partly explained.
The reproduced 128-read hang shows that two replica words do not guarantee completion.
The effects of the actual ticket graph, driver version, and other GPU users remain unknown.
An isolated repeat or a more direct driver trace must confirm the exact queue-cycle claim.
Task 3 does not start, and this work leaves no production fix.
